# Commission and invoice month-end (Phase A: manual)

Owner and escalation contact: Takib. Covers the end-of-month partner
commission review. **This process is explicitly manual in Phase A** —
IMPLEMENTATION_PLAN §19 places invoice generation/approval UI in Phase B
(REQ 04's portal), and no `POST .../invoices` route exists in
`apps/backend/src/routes/staff.ts` today. Do not invent an invoice-generation
feature to follow this runbook; the manual process below is the intended
Phase A behaviour, not a stopgap you need to route around.

## Required access

- Staff session with `financial.read` (Finance or Owner role) to view
  commission amounts — the Partners role can see partner/commission
  *records* but never amounts (`docs/API.md`: "a Viewer sees states but no
  money").
- Every Finance/Owner privileged action needs a session that completed MFA
  this login (`aal2`).
- Whatever the owner uses today to actually pay partners outside this system
  (bank transfer portal, accounting spreadsheet) — out of scope for this
  repository.

## What exists in code today

- **Commission lines are created automatically** when a partnered order
  activates (`apps/backend/src/partners/activation.ts`,
  [dispatch-and-activation.md](dispatch-and-activation.md)). Each line
  snapshots the effective commission rule (`commission-rule.ts`:
  `selectEffectiveRule` — the rule with the latest `effectiveFrom` whose
  window contains the activation instant) so a later rule change never
  retroactively alters an already-earned line.
- **Commission state machine**: `earned` → `carrier_paid` → `partner_paid`.
  Phase A code only supports moving a commission to `carrier_paid`
  (`POST /workspaces/{id}/partners/{partnerId}/commissions`, requires
  `financial.read`). Marking `partner_paid` is **hard-disabled** in code —
  the route returns `409 feature_not_ready` for that target state
  (`PAYOUT_DISABLED_REASON` in `staff.ts`) until OPEN_INPUTS #18 defines an
  interim approval mechanism, or B1 ships real invoice approval. Do not look
  for a workaround; this is intentional.
- **No invoice object exists in Phase A.** "Invoice month-end" today means:
  review earned/carrier-paid commission lines and reconcile them against
  whatever the owner pays partners through outside this system — there is no
  in-app draft/approve/regenerate invoice flow to run yet, despite
  IMPLEMENTATION_PLAN §19's row implying one is planned for later phases.

## Monthly manual process

1. In admin, open each partner's detail (`/w/<workspace>/partners/{id}`) with
   a Finance/Owner (`financial.read`) session. The response includes
   `commissions` (only visible with `canViewPayouts: true`),
   `canMarkCarrierPaid`, and `partnerPaidEnabled: false` with
   `payoutDisabledReason` explaining why.
2. For each partner, list commission lines with `status: earned` for the
   month being closed. Each line carries its frozen rule snapshot (rule id,
   type, amount/currency, effective window) — this is the authoritative
   amount, not a recomputation.
3. Cross-check the earned lines against the referred orders
   (`detail.referredOrders`) to confirm each line corresponds to a real
   activated order for that partner, for sanity before payout.
4. Reconcile the total against the owner's actual outbound payment process
   (bank transfer, accounting tool — outside this codebase). This step is
   entirely manual; there is no export or invoice PDF generated by the
   application today.
5. Once a commission line's carrier-side amount has actually been paid out,
   mark it `carrier_paid` via
   `POST /workspaces/{id}/partners/{partnerId}/commissions` with
   `{ commissionId, toState: "carrier_paid" }`. This requires `financial.read`
   (Finance's privileged action, `aal2`).
6. Do **not** attempt to mark a line `partner_paid` — the route will return
   `409 feature_not_ready`. Track final partner-paid status outside the
   application (spreadsheet, accounting system) until this is built.
7. Record the reconciliation (which lines were reviewed, totals, any
   discrepancies) wherever the owner keeps month-end records today — this
   repository has no audit surface specifically for the manual reconciliation
   step itself, only for the `carrier_paid` state transition (which is
   audited automatically like every staff write).

## Verify

1. Every commission line moved to `carrier_paid` this month shows that state
   and a `history` entry with the acting staff member and timestamp
   (returned by the state-change response).
2. `partner_paid_disabled` / `feature_not_ready` is never worked around by a
   direct database update — if you find a row with `state = 'partner_paid'`
   that wasn't set through a supported path, that is itself an incident to
   escalate, not something to replicate.
3. The reconciliation total matches what was actually paid out through the
   owner's external payment process.

## Safe stopping point

This process is safe to pause between partners — each partner's commission
review is independent, and moving a line to `carrier_paid` is a discrete,
audited action with no follow-on side effects that require the rest of the
review to happen in the same session.

## Escalation

Escalate to the owner (Takib) for: any commission line whose effective rule
looks wrong (check `selectEffectiveRule`'s window logic before assuming a bug
— a rule change only affects lines activated *after* its `effectiveFrom`), a
`percentage`-type rule (basis and rounding are OPEN_INPUTS #17, unresolved —
these should not produce a computed amount at all;
`CommissionConfigIncompleteReason` should already have blocked activation in
that case), and always for any request to mark a line `partner_paid` — that
capability does not exist yet and must not be simulated with a direct write.
