## Correctness repairs

- G12 — added `listDrainableEvents` and `CatalogueService.drainEvents`: one
  bounded pass over the workspace's pending events plus failed events still
  below the attempt bound, in deterministic `createdAt, id` order, with each
  event's failure recorded and skipped so one poison delivery cannot block the
  queue. T10B schedules it with `reconcile` under the existing `reconcile:run`
  scope.
- G13 — provider adapters are an explicit, non-production opt-in
  (`OUTBOX_ADAPTERS=fake`). A production or unset deployment registers handlers
  that fail permanently with `provider_not_configured`, so a claimed job is
  recorded as failed in admin rather than completing under a fake provider id.
- G14 — request-error logging is PII-safe (`logRequestError`), and the orders
  route returns `503` only for connection-level failures and `500` otherwise,
  instead of misreporting an application error as a provider outage.
- G16 — a completed-idempotency-key retry is bounded by
  `ORDER_RETRY_WINDOW_MS` (24 hours) measured from `completedAt`; outside the
  window the caller receives `draft_expired` rather than a replayed order.
- G19 — recorded the catalogue/order/outbox concurrency and identity decisions
  in `docs/ADR/0003-catalogue-orders-outbox.md`.
- G21 — a correctly signed but malformed webhook body (invalid JSON or an
  invalid payload shape) now returns `400 invalid_request` instead of falling
  through to a generic failure.
- G22 — webhook registry entries require `actorId`; the verified machine actor
  is persisted as `catalogue_sync_events.actor_id` (migration
  `0014_concerned_karen_page.sql`) and reused by every later inbox and sync
  write, so drain attribution is stable and never the event id or a random UUID.
- G23 — each handler runs under a per-handler abort timeout, recorded as
  `uncertain` with `handler_timeout` because the provider may already have
  accepted the work; a run deadline stops the runner claiming new batches while
  still handling and recording jobs already claimed under a lease.
- G24 — the `ORDER_OPERATIONAL_TRANSITIONS` switch is TEST-only and is ignored
  when `NODE_ENV=production`, so it can never authorize a real dispatch or
  activation.
- G25 — an operator requeue of a definitively failed job preserves the previous
  attempt's provider evidence (`provider_id`, `outcome`) and resets only the
  attempt and lease state.
- G26 — `reconcile` reads one `listPublished()` snapshot for the whole pass
  (no per-product N+1 listing), and its actor is required and registry-backed:
  the scheduler entry is resolved through
  `schedulerForWorkspace(workspaceId, 'reconcile:run')`, and the manual command
  fails closed with `reconcile_actor_unavailable` when no single non-revoked
  entry matches.
- G27 — added Sanity catalogue adapter unit tests and registered the adapters
  project with its own `vitest.config.ts`.
- G28 — site-1 catalogue revalidation invalidates a `plan:<productKey>` cache
  tag in addition to the `/plans` index.
- G29 — the runbook's command target `backend` was verified correct as written;
  no change required.
- G30 — the staging cron check cannot run without a dedicated staging Vercel
  project. Recorded as a pending external check below, not a pass.

## T10B — scheduled catalogue sync

Date: 17 September 2026

The already-tested T10 handlers are now registered with T15's authenticated cron
surface. `createCatalogueSyncRouter` exposes `GET`/`POST
/api/internal/catalogue/sync` (mounted at `/api/internal/catalogue` in
`app.ts`), mirroring `/api/internal/jobs/run`: it resolves the scheduler identity
through the server-only machine registry (`resolveScheduler`), requires the
existing `reconcile:run` scope selected by `CATALOGUE_SYNC_SELECTOR`, rejects
preview deployments, and derives its workspace set **only** from the verified
identity — never from a database tenant scan. `CatalogueSyncRunner` then runs,
for each authorized workspace in registry order, one bounded
`CatalogueService.drainEvents` pass followed by `CatalogueService.reconcile`
using the registry entry's `actorId`. A workspace whose drain or reconcile fails
records a bounded error code and the pass continues; a 120-second run deadline
stops starting new workspaces while work already in flight is recorded. No new
machine scope and no schema migration.

### What was exercised (disposable Postgres, freshly recreated)

`apps/backend/tests/catalogue-scheduled-pass.integration.test.ts` drives the real
runner against a migrated disposable database and covers the three cases the
task names, through the scheduled path rather than the manual handler:

- **Duplicate delivery** — the same delivery id accepted twice yields one inbox
  row (`duplicate: true` on replay); the scheduled pass reports `listed: 1`,
  `processed: 1` and writes exactly one offer version.
- **Out-of-order events** — an r2 delivery and an r1 delivery are both pending,
  with `created_at` forced so the stale r1 delivery drains _after_ the newer r2
  delivery; the pass converges on revision r2 with a single offer version, and
  both inbox rows complete against r2.
- **Missing webhook** — a product published in the CMS with **no** inbox event is
  created by the reconciliation half alone (`listed: 0`, `reconciled: 1`), at the
  current revision and unrevoked.

Route-level unit tests (`catalogue-sync-route.test.ts`) prove the unauthorized
paths: a wrong secret returns 401, an `outbox:run`-only scheduler returns 403, a
preview deployment returns 403, and only the registry-authorized workspace set
reaches the runner with the persisted actor. `catalogue-runner.test.ts` proves
the deadline stops new workspaces without abandoning the one in flight, that a
failing stage is recorded while the remaining workspaces continue, and that
per-event drain failures surface in the summary.

### Staging cron check — NOT performed (G30 remains open)

The schedule has **not** run on a deployed environment, and this is not a pass.
The mechanism has changed: the backend now runs an **in-process scheduler** on
Railway (outbox every 60s, catalogue sync every 300s;
[ADR 0004](../ADR/0004-backend-on-railway.md)) instead of a five-minute Vercel
cron, because Railway cron has a five-minute floor and a sub-daily Vercel
expression failed the whole backend deployment on the Hobby plan. The Canadian
Plans Vercel team has zero projects, the Railway service is not provisioned yet,
and no deployment credentials are available from this working environment.
OPEN_INPUTS #22 records the owner decision "Single live environment — no separate
staging project". Phases 0–6 of the migration (scheduler, container, config,
docs) are complete, but they are **not** evidence that the hosted schedule works.
Closing G30 requires:

1. A provisioned, non-preview Railway deployment with `ENABLE_SCHEDULER=1`.
2. `MACHINE_REGISTRY_JSON` with a single non-revoked scheduler entry holding
   `outbox:run` and `reconcile:run`, an explicit `actorId`, and the explicit
   deployment workspace UUID set; `JOB_RUNNER_SELECTOR` and
   `CATALOGUE_SYNC_SELECTOR` selecting it; `CRON_SECRET` matching its `secret`
   (`docs/ENV.md`).
3. Observed scheduler tick timestamps and the resulting sync state recorded here,
   plus a manual `POST` request/response.

Until those exist, the authenticated manual `POST /api/internal/catalogue/sync`
and the local `catalogue:job` command remain the invocation paths
(`docs/RUNBOOKS/catalogue-sync.md`). Only Phase 8's observed Railway evidence may
close G30; do not mark it closed on the strength of the local Phases 0–6 gate.
