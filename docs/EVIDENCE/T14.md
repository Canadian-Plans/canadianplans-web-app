## Implementation notes

- Every write is a backend endpoint carrying `expectedVersion`. The admin holds no transition, payment, cancellation or amendment rule; `allowedTransitions` and `capabilities` are computed server-side and the UI renders exactly them.
- The submitted order envelope is immutable (`app.prevent_order_submission_mutation`, invariant 5), so an approved change request writes its own audited `app.order_amendments` row (REQ 14) and applies the contact half to the originating lead; form-field corrections live in the amendment.
- Notes and reminders are separate child records, so adding one never races a colleague's status transition on the order's version.
- Dispatch writes `app.dispatch_records` in the same transaction as the Dispatched transition (invariant 7).
- Permission-aware search: `workspace.read` may always search the reference; matching customer name/email/phone requires the same capability as `order.manage` or `financial.read`, with substring (`strpos`) matching, not `LIKE`, so a term cannot inject a wildcard pattern. Documented in `docs/API.md`.
- Production dispatch/activation remain gated by `ORDER_OPERATIONAL_TRANSITIONS` (ignored when `NODE_ENV=production`); partnered activation still returns `feature_not_ready`, and the admin surfaces it instead of hiding the button.

### Limitation

A live Playwright order journey requires a real Supabase Auth staff session, which CI and preview deployments do not have (invariant 13). The end-to-end journey is proven by the stateful component test above; `apps/admin/e2e/README.md` records the staging steps to add the browser version.
