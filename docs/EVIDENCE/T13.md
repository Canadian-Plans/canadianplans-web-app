# T13 — SIM order form on site-1

Date: 17 September 2026

## Scope

The multi-step order form at `apps/site-1/order` (Plan → Details → Documents →
Review + terms → Confirmation), the four shared primitives it needs, and the
website-scoped published-offer read it depends on. All order data goes through
the backend typed client (`@canadian-plans/contracts`); site-1 never touches the
database. Production publishing, dispatch, activation and payout remain disabled
behind their unresolved inputs.

## Delivered

- **Shared primitives** (`@canadian-plans/ui`): `Stepper`, `FormField`,
  `FileDrop` (wired placeholder — real R2 upload is T17) and `ReviewCard`, with
  component tests and exports.
- **Website published-offer read**:
  `GET /api/v1/website/offers` — website credential with the existing
  `quotes:create` scope (no new scope), returning each currently available
  product's `productId`, `offerVersionId`, `lastSyncedAt` and the current
  immutable commercial snapshot, scoped to the credential's own workspace.
  Unavailable/revoked and invalid-content rows are excluded. This closes the
  data-path gap that previously made a selected plan impossible to quote:
  `POST /api/v1/quotes` needs a backend `productId`, but the storefront's content
  only carries a `productKey` and no website-scoped read exposed the UUID.
- **The order flow** (`apps/site-1/src/app/(storefront)/order/`):
  - `page.tsx` (server) loads the offers and captures attribution from the order
    URL and referrer header (`src/lib/attribution.ts`, mirroring the backend's
    allowlist; the backend remains the enforcer).
  - `order-form.tsx` (client) renders the five steps with the shared primitives.
  - `actions.ts` (server actions) calls the typed client: `POST /leads` at the
    end of step 2 with the save notice, later steps `PATCH` the same lead through
    its draft grant, step 4 issues `POST /quotes` then `POST /orders`.
  - `draft.ts` keeps the scoped draft grant and the ONE idempotency key per draft
    in an httpOnly cookie; the key is generated once, on the first successful
    lead save.
  - Preview deployments are `noindex` (`VERCEL_ENV=preview`).
- **End-to-end harness** (`apps/backend/tests/e2e/harness.ts`): boots the REAL
  backend app (`createApp`) against a disposable Postgres with two test-only
  seams — a stub published-catalogue provider (no live Sanity project is
  available) and an admitting bot check (the production verifier deliberately
  rejects Cloudflare's public test secrets). A small HTTP proxy fronts the app so
  a test can drop the response of an already-committed `POST /api/v1/orders`.

## Review fix — a returning customer can order a second plan

Found in review (17 September 2026) and fixed here. The draft cookie
(`cp_order_draft`, path `/order`, 30-day TTL) deliberately survives a
successful submission so a customer who lost the confirmation response retries
onto the SAME order. But `saveDetails` then PATCHed that finished draft, the
backend correctly refused with `draft_already_submitted` (409, the T12 G1
guard), and `failureFrom` had no branch for that code — so it fell through to
"Your order was not saved. Please try again." at step 2, permanently, on a
cookie the customer cannot clear. Every Playwright test uses a fresh browser
context, so no existing test covered it.

`saveDetails` now catches a finished-or-lapsed draft
(`draft_already_submitted`, `draft_expired`, `draft_not_found`) from the resume
PATCH and starts a brand-new draft — new lead, new draft grant, new idempotency
key. Any other backend failure still surfaces as `not_saved` and creates no
second lead. `failureFrom`/`quoteFailureFrom` also map
`draft_already_submitted` to an accurate "that order has already been placed"
message instead of the misleading save failure.

Regression test: `apps/site-1/src/app/(storefront)/order/actions.test.ts` — the
resume path keeps one lead and one key; each finished-draft code starts a fresh
draft with a different key; a `persistence_unavailable` failure still reports
`not_saved` and creates no second lead. The three finished-draft cases fail
against the pre-fix action and pass after it.

## Review fix — e2e suite rate-limited itself (Gate A2 reliability)

The first CI run of the merged branch passed but reported **1 flaky** test:
`[mobile] a quote failure offers a callback and creates no order` timed out for
30s waiting for the step-1 plan link, then passed on retry.

Cause: the harness wired the REAL website rate limiter with the production
defaults (`DEFAULT_WEBSITE_RATE_LIMITS` — 120 requests per IP per 60s). Every
Playwright request reaches the backend from the same client IP (`127.0.0.1`,
via the harness proxy), and the 30-test suite makes roughly ten website calls
per order test within overlapping 60-second windows. Late in the run the IP
bucket is spent by the suite's own traffic, `GET /api/v1/website/offers`
returns 429, `order/page.tsx` sets `loadFailed` and renders "Plans are
unavailable right now", and no plan link ever appears.

This is an artifact of co-located test traffic, not behaviour the journey should
assert — and it is a Gate A2 risk, because T16 adds more traffic on the same IP,
so the flake rate rises and Playwright's two CI retries mask it
non-deterministically.

Fixed by using the already-injectable `WebsiteAuthDependencies.limits` seam: the
harness now raises the thresholds (documented as the harness's third and last
test seam). The limiter is still the real DB-backed one and still runs on every
request; only the numbers move, and they stay finite so a runaway loop in a
journey is still caught. `choosePassportPlan` additionally asserts the
"Plans are unavailable right now" card is absent, so any future recurrence
names its cause instead of timing out on a locator.
